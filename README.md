# osu!mania 匹配赛模拟器（Pygame）

一个用 Pygame 写的 **osu!mania 对战模拟器**：它不让你操作，而是让两队（各 3 名"选手"）
在同一张 4K 谱面上各打一遍，把分数、准确率、连击和判定实时演出来，最后按大比分决出胜负。

选手的能力值由**名字哈希**生成（体力/手速/准度），每次击打都由概率模型决定是否打中，
所以同一份配置也会打出不同的过程，但换名字就等于换人。

## 运行

```bash
# 1) 安装依赖（只需要 pygame；pygame-ce 对 Python 3.13/3.14 支持更好）
python -m pip install -r requirements.txt

# 2) 启动（默认读取项目根目录的 config.toml）
python main.py

# 也可以用别的配置文件
python main.py --config my_match.toml
```

对局中按 `Esc` 或关闭窗口即可退出。

## 配置：只有一份文件

**所有配置都在项目根目录的 `config.toml`**，改这一份就够了：
画面、比赛规则、判定窗口与分值、曲库、队伍与玩家、每轮选曲顺序。
旧版的 `data/songs.txt`、`config/teams.txt`、`config/choose.txt` 已经全部并入这里，不再读取。

| 配置段 | 作用 |
| --- | --- |
| `[game]` | 窗口尺寸、帧率、音符提前进入视野的距离、各界面停留时长、调试信息 |
| `[match]` | 比赛名、几胜制、结果记录文件、是否续接上次未打完的比赛 |
| `[judge]` | 判定窗口（毫秒）、每个判定的基础分、连击奖励的增减与上下限 |
| `[players]` | 每首歌开始时是否重新读取队员名单（`reread_roster`）、手感波动幅度（`form_range`） |
| `[pool_colors]` | 选曲列表左侧分类标签的颜色（按曲目 id 前两个字母取色） |
| `[[songs]]` | 曲库：每首歌的 id / 标题 / 艺术家 / 谱面文件夹 |
| `[[teams]]` | 队伍与玩家：必须是 2 支队伍，每队 1~3 名玩家 |
| `[[picks]]` | 选曲顺序：每轮一首，可指定由哪队选；用完后自动在曲库里循环 |

配置里的**相对路径都相对于 `config.toml` 所在目录**，所以从任何目录启动都能找到资源。
配置写错时程序会在启动阶段打印明确的中文错误（哪个段、哪个键、期望什么），不会只抛一堆 traceback。

### 曲目文件夹

`[[songs]]` 的 `folder` 指向一个谱面目录：

```
data/beatmaps/2598781/
    xxx.osu      # 只有一个 .osu 时自动识别，也可以在 config.toml 里用 beatmap 指定
    audio.mp3    # 优先用 .osu 里 AudioFilename 指定的文件，其次 audio.mp3/.ogg/.wav
```

本模拟器按 **4K（CircleSize:4）** 处理谱面，其他键数的谱面会在启动时给出警告。

## 比赛流程

一个完整循环是 `MENU → SONG_SELECT → PLAYING → RESULTS →（回 SONG_SELECT 或 FINISHED）`，
每个阶段停留多久都由 `[game]` 里的四个等待时间控制：

| 阶段 | 等待参数 | 这段时间在做什么 |
| --- | --- | --- |
| `MENU` | `start_delay` | 启动后的等待，画面展示曲库与已选曲目 |
| `SONG_SELECT` | `song_select_delay` | 试听本轮曲目；**选曲的这一刻会重新结算全部选手**（见下一节）并把能力值打到控制台 |
| `PLAYING`（开打前） | `match_start_delay` | 音符还没开始滚，音乐在这段结束后才响起（歌曲时间归零） |
| `RESULTS` | `results_delay` | 展示本局成绩：两队每名选手的分数/准确率、本局胜者、大比分 |

之后谱面发完、所有人手上没有音符、音乐也放完后结算本局，把胜者追加进赛果缓存（见下）。

### 赛果缓存

每局打完，**到本场为止的全部赛果**都会立刻写回 `config.toml` 的 `[match] results`：

```toml
[match]
rounds_to_win = 2
resume = true          # true = 启动时读取下面的缓存接着打；false = 忽略并清空缓存重开一场
results = [0, 1, 0]    # 每局一个胜者序号（0 = 第一支队，1 = 第二支队），程序自动维护
```

- 启动时按 `results` 重建大比分：没打完就接着打，并打印「已打 N 局，大比分 x:y」；
- 缓存里的比赛**已经分出胜负**时没法接着打，会打印提示并自动清空缓存、重新开一场
  （原来那份成绩还能在改之前的 `config.toml` 里翻到）；
- 写回时会**只改 `results` 这一行**，文件里的注释和其它配置段原样保留；
  采用「先写临时文件再整体替换」，中途失败也不会把配置写坏；
- 想手动重开一场：把 `results` 清成 `[]`，或把 `resume` 改成 `false`。

有队伍达到 `rounds_to_win` 胜则 `RESULTS` 结束即进入 `FINISHED`，否则回到 `SONG_SELECT`。

### 计分赛模式

`[match] score_mode = true` 切到计分赛：**不管 `rounds_to_win`**，把 `[[picks]]` 里写的曲目
按顺序各打一遍，然后按所有曲目的总分排名，并把成绩写进 Excel。

- `[[songs]]` 是**曲库**（可选曲的池子），`[[picks]]` 才是计分赛**实际要打的曲目表**；
  例如曲库 5 首、picks 只写了 3 条，那就只打这 3 首。
- 没写 `[[picks]]`（或里面的 id 一个都对不上曲库）时，退化成打整个曲库。

```toml
[match]
score_mode = true
excel_file = "data/score_match.xlsx"   # 成绩表写到这里（相对路径基于 config.toml）
```

- 打完后把 **两队队名与队员、每首歌的分数、总分** 写进 `excel_file`：
  表头是 `队伍 | 队员 | Track1 | Track2 | ... | 总分`，每队先各队员一行（逐曲分数），
  再一行「队伍总分（第 N 名）」，表末附上 Track 与歌名的对照。
  写 xlsx 没有引入任何第三方库（`src/utils/excel.py` 按 OOXML 规范直接拼 zip），
  数字是真数值单元格，在 Excel 里可以直接求和。
- 结算画面不再显示「谁赢」，改成**总分排名榜**：中间一列是 `Track1 / Track2 / ... / Total / Rank`，
  两侧各占一队、各自在自己那半屏居中，每首歌总分一行，倒数第二行是全部曲目的总分、
  最后一行是名次 `1st / 2nd`；最后两行字号更大，分数千分位分隔。
- 计分赛**总是重新开一场**（结算榜和 Excel 需要完整的逐曲成绩，没法从缓存接着算），
  启动时会打印说明并清空缓存。
- 计分赛里**不会触发赛点紧张**：`rounds_to_win` 在这个模式下无效，
  「再赢一局就夺冠」的压力无从谈起（否则 `max(比分) >= rounds_to_win - 1` 会一直成立）。


- **等待期间**（MENU / SONG_SELECT / 开打前 / RESULTS）在**左下角**显示 `Countdown:xx`，
  xx 是距离"比赛真正开始"的剩余秒数。这是跨阶段累计的 ——
  在 MENU 阶段会把后面两个阶段一起算进去，所以从启动开始它是一路连续倒数到 0 的；
- **比赛开始后**在**屏幕中央**显示已结算音符占总音符数的占比，只有数字（例如 `34.2%`）。


## 选手能力值

每首歌开始时都会重新结算一次：

1. 若 `[players] reread_roster = true`，先重新读取 `config.toml` 的 `[[teams]]`
   —— 改完名单不用重启，下一局生效；配置写坏了只警告并保留原名单，不影响正在进行的比赛；
2. 重新生成本局能力值：**基准 + 风格偏置 + 本局手感**。
   基准和风格完全由名字哈希决定（同一个名字每局底子一样），
   手感只浮动**体力 / 手速 / 准度**三项、各随机 ±`swing`，
   而 `swing = form_range × (1 - 0.75 × 稳定性/100)`
   —— 所以**稳定性决定每局的波动幅度**，越稳的选手越不容易大起大落；
   **稳定和心态不参与手感**（稳定是拿来决定手感幅度的，不能被手感反过来改；
   心态同属"底层特质"），每局恒为基准值；
3. 把本局每名队员的风格与能力值打到控制台（括号内是本局手感偏移）。

五项能力的分工（判定用的是"落点误差"模型，见下）：

| 能力 | 作用 | 实测影响（低难 Lian Fan / 高难 [42]） |
| --- | --- | --- |
| 手速 `speed` | 能从容处理多密的同键间隔；跟不上时误差被放大、整体打晚 | 3.5pp / **34.2pp** |
| 体力 `stamina` | 耐久：池子越空落点越飘越晚，后半段开始漏 | 2.0pp / **10.8pp** |
| 体力回复 | 一只手空档超过 400ms 的部分按 60/秒回体力，回满为止 | 密谱几乎回不到（RC2 终盘 +7pp），稀疏谱因为本来就满池，回复大多被"不能超过满池"削掉 |
| 准度 `avg_accuracy` | 落点误差的地板（只影响打得多准，不会凭空漏键） | 3.4pp / 6.5pp |
| 稳定 `consistency` | 长条**松手**的精度 + 每局手感幅度（不影响按下的精度） | 0.9pp / 1.4pp；另有手感幅度：稳定 14 手感 ±18，稳定 100 手感 ±5 |
| 心态 `mentality` | 连击 **>500** 且**体力已经吃紧**（疲劳 > 0.25）时"手抖一下"：落点被推后约 120ms，判成 BAD 或擦边 MISS | 0.15pp / 0.38pp；体力宽裕的谱（低难图）**完全不会触发**，只在长连击 + 体力吃紧的后半段出现 |

### 落点误差模型
每个音符**只结算一次**（在它到点的那一帧），选手一定会去按 —— 没有"按不按键"的随机，
只有"按下去的时刻偏了多少"：

```
press_offset = μ + N(0, σ) + 手抖
σ = 准度地板(1.5~12ms) + 密度压力²×38 + 疲劳×15
μ =                    密度压力²×50   + 疲劳×22
密度压力 = max(0, 手速决定的间隔 / 实际同键间隔 - 1)
手抖     = 连击>500 且体力吃紧时，按概率给落点加 N(120ms, 45ms)
判定 = get_judgement(press_offset)   超过 bad 窗口 = 漏键
```

**长条松手**是另一次判定，口径与点击有三处不同：

```
release_offset = μ + N(0, σ)
σ = (准度地板 + 疲劳×15 + 不稳定×3) × 1.8      # 唯一吃「稳定性」的地方
μ =             疲劳×22                         # 不吃手速、也不消耗体力
```

也就是说**稳定性只作用在松手上**：按下那一下不看稳定（实测稳定 0 与 100 的按下 σ 完全一致），
松手却随稳定明显变化（稳定 0 的松手 σ 比稳定 100 大 3.6~5.7ms）。
稳定性另一个作用仍然是**每局手感幅度**（稳定 14 → ±18，稳定 100 → ±5，`form_range=20` 时）。

漏键只有两个来源，都是"有原因"的：
1. **跟不上 / 累了** —— 密度压力和疲劳把 σ、μ 顶上去，误差真的超出判定窗口；
2. **心态手抖** —— 连击 **>500**、**并且体力已经吃紧**（疲劳 > 0.25）时才会发生，
   表现为 BAD 或擦边 MISS。压力大小取"还剩多少体力"的补数并带死区，
   所以体力宽裕时**根本不会掷这个骰子**：低难图（几乎不掉体力）配上合格的耐力
   可以稳定 FC，压力天然集中在长歌后半段和密谱上。

   实测（每档 6 局，手速 80 / 准度 70 / 稳定 70）：RC1 这种低难图在
   心态 90~0、体力 90~30 的所有档位都是 **6/6 FC、0 次手抖**；
   而 RC2 那种硬谱仍随心态明显分化（90 心态 0.8 次/局 → 0 心态 4.2 次/局）。

   「自己分高」和「进入赛点」会再放大这个概率，但**计分赛不会吃赛点倍率**
   （那个模式下没有"再赢一局就夺冠"这回事）。

（每轮把时间往前推 100ms）把整场比赛尽快跑完，分数与赛果打到控制台：

```toml
[game]

```

```
第 1 局 RC3 Science (feat. Kasane Teto SV)
  ★ The Wanderers     2,953,213
    Gamer Two         2,926,751
    → The Wanderers 拿下本局，大比分 1:0
...
比赛结束：3:0，The Wanderers 获胜
赛果表已写入 Excel: .../data/match_results.xlsx

```

三首计分赛（虚拟时间 596 秒）实测 **0.6 秒**跑完。判定逻辑与正常对局完全一致 ——
见下面「为什么无 UI 不会算错」。

### 赛果表（常规比赛）

**不管开不开无 UI、是不是计分赛**，比赛一旦决出胜负，就会把每一局双方得分写进
`[match] results_excel`（默认 `data/match_results.xlsx`）：

| 局 | 曲目 | 曲目 id | The Wanderers | Gamer Two | 本局胜者 |
| --- | --- | --- | --- | --- | --- |
| 1 | Science (feat. Kazane Teto SV) | RC3 | 2953212.6 | 2926750.8 | The Wanderers |
| … | | | | | |
| 大比分 | | | 3 | 0 | The Wanderers 获胜 |

这是**另一个** Excel —— 计分赛那份 (`excel_file`) 是逐曲逐人的成绩明细，这份是每局双方的赛果。

### 为什么无 UI 不会算错

推进步长从 16.7ms 放到 300ms，结果**逐位相同**（本机调试脚本里对这一点有断言）。
为了做到这点顺手修了两个模型本身的帧率依赖：

1. **结算顺序**：原来一帧里"先把所有点击判定做完，再做所有长条松手判定"，
   跨越同一帧的一次点击和一次松手谁先结算会取决于帧长。现在 `play()` 每次只挑
   **最早该结算的那一个**再重新挑，严格按时间顺序结算。
2. **随机流**：6 名选手原来共用全局 `random`，各人抽数的先后会随"这一帧谁结算了几个音符"变化。
   现在**每个选手一条独立的 `random.Random`**（种子从全局流取，所以 `random.seed(N)` 仍可复现整场）。

### 体力是怎么算的

两只手各有一个 10000 的池子（左手轨道 0/1、右手轨道 2/3），`fatigue` 取两手的平均值。
**每首歌开始时满血重置**（跨曲不累积），一首歌之内：

- **消耗**：每按一下扣 `3 × clamp(250/同键间隔, 0.4, 3) ÷ 效率`，效率 = `0.4 + 1.2 × 体力/100`。
  越密越费，而且有个 0.4 的地板 —— 所以"音符本身存在"就占了总消耗的 30~40%；
- **回复**：这只手距离上一次出力**空档超过 400ms** 的部分，按 **120/秒** 回体力，回满为止。
  注意回复看的是"整只手"的空档，不是单条轨的间隔 —— 两条轨轮流砸的时候轨间隔可能不小，
  但那只手其实一直在动。

所以体力是**大进大出**的：密段哗哗掉，空档又哗哗回。实测（体力 50、终盘 / 最低 / 摆幅）：

| 曲目 | 终盘 | 最低 | 摆幅 |
| --- | --- | --- | --- |
| RC1（稀疏） | 78% | 78% | 22 |
| RC2（最密） | 22% | 18% | 82 |
| RC3 / LN1 / HB1 | 67% / 67% / 69% | 同左 | 32~33 |

要保住"终盘 40%"所需的体力：RC1 只要 1，RC3/LN1/HB1 要 14~20，RC2 要 70。

**只有 miss 会断连**（BAD 不断连），所以手抖的那一下多半表现为掉分 + 偶尔断连。

**准度没有"随机漏键"通道**：它只决定 σ 的地板，所以低准度选手是"判定差、分数低"，
而不是"时不时莫名漏一个"。

### 长条（LN）

谱面里的长条是 `type` 带 128 位、末位带结束时间的行：

```
448,192,25078,128,0,26641:0:0:0:0:
  x    y   开始  类型 音效  └ 结束时间
```

- **渲染**：一个和普通音符完全一样的头（白色 35×10），加一条**颜色更深、更窄**的身
  （深灰 `(110,110,110)`、21px 宽），从头上方一直连到结束时间的位置；
  已经按住时头不再绘制，身则从判定线往上保留。受"挡板"限制，
  身体和普通音符一样只在最后约 400ms 的窗口里可见（`max_render_dist` 决定）。
- **判定**：头打中才开始按住，**松手时还有一次额外判定**。松手判定和点击判定的区别只有两条：
  1. **不吃手速** —— 它不算同键间隔，因此没有密度压力项，也**不消耗体力**
     （手速只作用于点击判定）；
  2. 更容易打偏 —— 落点误差 σ 乘 `LONG_RELEASE_SIGMA_SCALE`（默认 1.8）。

  其余（准度地板、疲劳、稳定性、判定等级、分数、连击）和点击完全一样。
- 头没打中 → 整根算一次 miss，不再有松手判定；松手判定 miss 同样断连。
- 满分按**判定次数**算：普通音符 1 次、长条 2 次（`Song.judgement_count`），
  所以插了长条不会让标准化分数虚高。

### 画面上的判定计数

游玩中每个选手的演奏区两侧各有一列竖排小字，每行一个判定、顺序固定：

| 行 | 判定 | 颜色 |
| --- | --- | --- |
| 1 | 完美+ `perfect_g` | 黄 |
| 2 | 完美 `perfect` | 橙 |
| 3 | 很好 `great` | 绿 |
| 4 | 好 `good` | 蓝 |
| 5 | 差 `bad` | 淡灰 |
| 6 | 漏 `miss` | 红 |

数量为 0 的那一行不画字，但**行位保留**，所以红色的 miss 永远落在第六行。

- 第一队（红队）贴在**第四轨右侧**，左对齐；
- 第二队（蓝队）贴在**第一轨左侧**，右对齐。

字号由 `JUDGEMENT_COUNT_FONT_SIZE`、颜色由 `JUDGEMENT_COUNT_COLORS`（都在 `src/core/game.py` 顶部）控制。

漏键不是掷骰子掷出来的，而是"误差超出判定窗口"的结果。**σ 各项是相加的**，这一点决定了难度分化：

- **低难图**：密度压力≈0、几乎不疲劳 → σ 基本只剩准度那一项 → 人人都在 99% 上下，靠准度比小数点；
- **高难图**：密度压力把 σ 顶到几十毫秒，准度那几毫秒的差别被彻底淹没 → 手速和耐力决定上限。

选手风格由名字哈希决定（手速型 / 耐力型 / 稳准型 / 爆发型 / 大心脏 / 赌徒 / 天才…），
风格给五项加不同偏置，所以"换个名字"就是换一个完全不同的人。

上面的数字来自本机的标定脚本（跑真实谱面做扫参），那些脚本属于调试工具，没有进版本库。

### 单独查一个名字：`ability.py`

想给选手起名字之前先看看他会拿到什么能力值，用这个独立小工具（不依赖 pygame、
不读谱面、不启动游戏，只跑名字哈希那一段逻辑，结果和游戏里完全一致）：

```bash
python ability.py Red-1                  # 查一个名字（基准 + 风格 + 手感 + 一局样例）
python ability.py Red-1 Red-2 阿夸        # 多个名字给表格（中英文自动对齐）
python ability.py --rolls 5 Red-1        # 连抽 5 局，看看手感波动范围
python ability.py --form 0 Red-1         # 关掉手感，只看基准
python ability.py --styles               # 打印 8 种选手风格各加什么偏置
python ability.py                        # 交互模式：一行一个名字，空行结束
```

手感幅度的默认值直接读 `config.toml` 的 `[players] form_range`，所以和游戏是同一套参数。

### 算赛谱的长条占比与能力要求：`chart_report.py`

把 `config.toml` 里所有赛谱扫一遍，算出**长条占比**和**手速/体力要求**，写成一份 Excel
（同样不依赖 pygame，只走谱面文本解析）：

```bash
python chart_report.py                          # 读 config.toml → data/chart_report.xlsx
python chart_report.py -c my.toml -o out.xlsx   # 指定配置与输出
python chart_report.py --free 0.03 --keep 30    # 调两个阈值
python chart_report.py --no-excel               # 只在控制台看
```

两个"要求"不是拍脑袋定的，而是**反推主程序那套落点误差模型**：常量直接从
`src/entities/player.py` import，主程序改模型时这份报告自动跟着变。

- **手速要求**：让整张谱的**平均密度压力**降到阈值（默认 0.05）以下所需的最低手速。
  密度压力 = `max(0, 所需间隔/同键间隔 − 1)²`，所需间隔 = `230 − 145 × 手速/100`。
  另外两列是同一口径的尖峰版本：
  **最快5%段手速**（段长 = 总音符数 × 5%，沿时间顺序滑动取最吃力的连续一段）
  和**最密处手速**（单点尖峰）。三者天然满足「全曲 ≤ 最快段 ≤ 最密处」。
- **体力要求**：打完这张谱后体力池平均还剩 `keep%`（默认 40%）所需的最低体力。
  每按一下消耗 `2 × clamp(250/同键间隔, 0.4, 3) ÷ 效率`，效率 = `0.4 + 1.2 × 体力/100`，
  所以可以解析反解，不用跑模拟。
- **长条占比** = 长条数 / 总音符数，判定与游戏一致（`type & 128` 且结束时间晚于开始时间）。
  表格里还有音符数、平均长条时长、每秒音符（中位/峰值）、同键间隔 P10/中位/P90 等辅助列。

本机的验证脚本会把解析结果和真实模拟器对撞：实测
「体力 50 时的终盘剩余体力」解析值与模拟值完全吻合（82.1/82.1、45.9/45.9、26.8/26.8），
手速要求也正好卡在压力阈值上。
