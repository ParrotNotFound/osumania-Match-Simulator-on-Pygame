# osu!mania 匹配赛模拟器（Pygame）

一个用 Pygame 写的 **osu!mania 对战模拟器**：它不让你操作，而是让两队（各 3 名"选手"）
在同一张 4K 谱面上各打一遍，把分数、准确率、连击和判定实时演出来，最后按大比分决出胜负。

选手的能力值由**名字哈希**生成（体力/手速/准度），每次击打都由概率模型决定是否打中，
所以同一份配置也会打出不同的过程，但换名字就等于换人。

## 运行

```bash
# 1) 安装依赖（只需要 pygame；pygame-ce 对 Python 3.13/3.14 支持更好）
python -m pip install -r requirements.txt

# 2) 启动（默认读取项目根目录的 config.toml）
python main.py

# 也可以用别的配置文件
python main.py --config my_match.toml
```

对局中按 `Esc` 或关闭窗口即可退出。

## 配置：只有一份文件

**所有配置都在项目根目录的 `config.toml`**，改这一份就够了：
画面、比赛规则、判定窗口与分值、曲库、队伍与玩家、每轮选曲顺序。
旧版的 `data/songs.txt`、`config/teams.txt`、`config/choose.txt` 已经全部并入这里，不再读取。

| 配置段 | 作用 |
| --- | --- |
| `[game]` | 窗口尺寸、帧率、音符提前进入视野的距离、各界面停留时长、调试信息 |
| `[match]` | 比赛名、几胜制、结果记录文件、是否续接上次未打完的比赛 |
| `[judge]` | 判定窗口（毫秒，半宽）。默认让窗口跟着谱面 OD 走；也可关掉改用固定值 |
| `[players]` | 每首歌开始时是否重新读取队员名单（`reread_roster`）、手感波动幅度（`form_range`） |
| `[pool_colors]` | 选曲列表左侧分类标签的颜色（按曲目 id 前两个字母取色） |
| `[[songs]]` | 曲库：每首歌的 id / 标题 / 艺术家 / 谱面文件夹 |
| `[[teams]]` | 队伍与玩家：必须是 2 支队伍，每队 1~3 名玩家 |
| `[[picks]]` | 选曲顺序：每轮一首，可指定由哪队选；用完后自动在曲库里循环 |

配置里的**相对路径都相对于 `config.toml` 所在目录**，所以从任何目录启动都能找到资源。
配置写错时程序会在启动阶段打印明确的中文错误（哪个段、哪个键、期望什么），不会只抛一堆 traceback。

### 曲目文件夹

`[[songs]]` 的 `folder` 指向一个谱面目录：

```
data/beatmaps/2598781/
    xxx.osu      # 只有一个 .osu 时自动识别，也可以在 config.toml 里用 beatmap 指定
    audio.mp3    # 优先用 .osu 里 AudioFilename 指定的文件，其次 audio.mp3/.ogg/.wav
```

本模拟器按 **4K（CircleSize:4）** 处理谱面，其他键数的谱面会在启动时给出警告。

## 比赛流程

一个完整循环是 `MENU → SONG_SELECT → PLAYING → RESULTS →（回 SONG_SELECT 或 FINISHED）`。
**选曲页会经历两个阶段**，而且从启动到开打**全程都有音乐**：

| 阶段 | 等待参数 | 画面 | 音乐 | 选曲状态 |
| --- | --- | --- | --- | --- |
| `MENU` | `start_delay` | 选曲页 | 放 `prelude_song`（留空 = 这场第 1 首） | **还没点出任何一首**，曲库不高亮 |
| `SONG_SELECT` 第一阶段 | `song_select_delay` | 选曲页 | 放**刚刚打完的那首**（第一局则是 prelude） | 仍然不点出下一首；第 2 局起高亮"上一轮打的那首" |
| `SONG_SELECT` 第二阶段 | `match_start_delay` | **仍是选曲页** | 开始试听**本轮曲目** | 点出下一首，高亮换成本轮（颜色 = 选这首歌的队伍） |
| `PLAYING`（开打前） | `preroll_delay` | 切到游玩页面 | 试听继续放 | 谱面**不动**、不判定 |
| `PLAYING` | — | 游玩中 | 音频从头开始 | 谱面开始滚、开始判定 |
| `RESULTS` | `results_delay` | 成绩画面 | 静音 | — |

关键点：

- **"点出下一首"发生在选曲页的第二阶段**，所以第一阶段结束前你都看不到下一首是什么；
  点出之后**不会立刻开打**，还会在选曲页上把这首试听 `match_start_delay` 那么久；
- 切到游玩页面后还要再等 `preroll_delay`（默认 1 秒）谱面才开始滚 ——
  这段里音频继续放，谱面停在原地；
- 倒计时（左下角 `Countdown:xx`）把前三个阶段加在一起连续递减，
  到"切进游玩页面"那一刻归零（preroll 那 1 秒不算进倒计时）；
- **`prelude_song`（start_delay 期间放的那段音乐）可以指向目录里的任意歌曲**，
  不必进 `[[songs]]`：

  | 写法 | 例子 | 行为 |
  | --- | --- | --- |
  | 留空 | `prelude_song = ""` | 放"这一场的第一首"（按 `[[picks]]` 算） |
  | 曲库 id | `"RC1"` | 放曲库里那一首 |
  | 音频文件路径 | `"data/bgm/opening.mp3"` | 直接放这个文件 |
  | 歌曲文件夹 | `"data/bgm/opening"` | 先按文件夹里 `.osu` 的 `AudioFilename` 找，再退回到第一个音频文件 |

  相对路径按 `config.toml` 所在目录解析（和 `[[songs]]` 的 `folder` 一样）；
  路径写错会打印中文提示并退回"这场第 1 首"，不会打断比赛。

之后谱面发完、所有人手上没有音符、音乐也放完后结算本局，把胜者追加进赛果缓存（见下）。

### 赛果缓存

每局打完，**到本场为止的全部赛果**都会立刻写回 `config.toml` 的 `[match] results`：

```toml
[match]
rounds_to_win = 2
resume = true          # true = 启动时读取下面的缓存接着打；false = 忽略并清空缓存重开一场
results = [0, 1, 0]    # 每局一个胜者序号（0 = 第一支队，1 = 第二支队），程序自动维护
```

- 启动时按 `results` 重建大比分：没打完就接着打，并打印「已打 N 局，大比分 x:y」；
- 缓存里的比赛**已经分出胜负**时没法接着打，会打印提示并自动清空缓存、重新开一场
  （原来那份成绩还能在改之前的 `config.toml` 里翻到）；
- 写回时会**只改 `results` 这一行**，文件里的注释和其它配置段原样保留；
  采用「先写临时文件再整体替换」，中途失败也不会把配置写坏；
- 想手动重开一场：把 `results` 清成 `[]`，或把 `resume` 改成 `false`。

有队伍达到 `rounds_to_win` 胜则 `RESULTS` 结束即进入 `FINISHED`，否则回到 `SONG_SELECT`。

### 计分赛模式

`[match] score_mode = true` 切到计分赛：**不管 `rounds_to_win`**，把 `[[picks]]` 里写的曲目
按顺序各打一遍，然后按所有曲目的总分排名，并把成绩写进 Excel。

- `[[songs]]` 是**曲库**（可选曲的池子），`[[picks]]` 才是计分赛**实际要打的曲目表**；
  例如曲库 5 首、picks 只写了 3 条，那就只打这 3 首。
- 没写 `[[picks]]`（或里面的 id 一个都对不上曲库）时，退化成打整个曲库。

```toml
[match]
score_mode = true
excel_file = "data/score_match.xlsx"   # 成绩表写到这里（相对路径基于 config.toml）
```

- 打完后把 **两队队名与队员、每首歌的分数、总分** 写进 `excel_file`。
  列布局是 `场次 | 比赛 | 队伍 | 队员 | Track1 | Track2 | ... | 总分`：
  每场开头有一行「曲目」（在各 Track 列里写明那一场打的是哪首歌），
  然后每队各队员一行（逐曲分数），再一行「队伍总分（第 N 名）」。
  写 xlsx 没有引入任何第三方库（`src/utils/excel.py` 按 OOXML 规范直接拼 zip），
  数字是真数值单元格，在 Excel 里可以直接求和。
- **成绩表是逐场累加的**：打完一场就追加在后面，换一支队伍再打不会覆盖之前的成绩
  （场次号自动 +1，旧行原样保留、仍是数值；如果之前是更早那版没有场次列的表，
  会整份并成第 1 场再往后接）。所以同一份 `excel_file` 可以一直用下去。
- **计分赛完全不显示胜负**：每打完一首（`RESULTS` 画面）和整场结束（`FINISHED`）都用同一张
  **成绩表**——中间一列是 `Track1 / Track2 / ... / Total / Rank`，两侧各占一队、在自己那半屏居中；
  每首歌的总分一行，倒数第二行是**目前为止的总分**，最后一行是它在表里的名次 `1st / 2nd`
  （最后两行字号更大、分数千分位分隔）。每打完一首，表就往下长一行，总分和名次实时更新；
  局中画面底部还会标 `已完成 N / M 首 · 总分与排名实时更新`，终局才显示成绩表文件写到哪。
  胜负字样（「谁拿下本局」「大比分」「第 N 局结束」）在计分赛里**一律不出现** ——
  普通模式照旧显示这些。
- 计分赛**总是重新开一场**（成绩表需要完整的逐曲成绩，没法从缓存接着算），
  启动时会打印说明并清空缓存。
- 计分赛里**不会触发赛点紧张**：`rounds_to_win` 在这个模式下无效，
  「再赢一局就夺冠」的压力无从谈起（否则 `max(比分) >= rounds_to_win - 1` 会一直成立）。


- **等待期间**（MENU / SONG_SELECT 两个阶段 / preroll / RESULTS）在**左下角**显示 `Countdown:xx`，
  xx 是距离"比赛真正开始"的剩余秒数。这是跨阶段累计的 ——
  从启动开始它是一路连续倒数到 0 的，归零的那一刻正好切进游玩页面（preroll 不算进去）；
- **谱面开始滚之后**在**屏幕中央**显示已结算音符占总音符数的占比，只有数字（例如 `34.2%`）。


## 选手能力值

每首歌开始时都会重新结算一次：

1. 若 `[players] reread_roster = true`，先重新读取 `config.toml` 的 `[[teams]]`
   —— 改完名单不用重启，下一局生效；配置写坏了只警告并保留原名单，不影响正在进行的比赛；
2. 重新生成本局能力值：**基准 + 风格偏置 + 本局手感**。
   基准和风格完全由名字哈希决定（同一个名字每局底子一样），
   手感只浮动**体力 / 手速 / 准度**三项、各随机 ±`swing`，
   而 `swing = form_range × (1 - 0.75 × 稳定性/100)`
   —— 所以**稳定性决定每局的波动幅度**，越稳的选手越不容易大起大落；
   **稳定和心态不参与手感**（稳定是拿来决定手感幅度的，不能被手感反过来改；
   心态同属"底层特质"），每局恒为基准值；
3. 把本局每名队员的风格与能力值打到控制台（括号内是本局手感偏移）。

五项能力的分工（判定用的是"落点误差"模型，见下）：

| 能力 | 作用 | 实测影响（低难 Lian Fan / 高难 [42]） |
| --- | --- | --- |
| 手速 `speed` | 能从容处理多密的同键间隔；跟不上时误差被放大、整体打晚 | 3.5pp / **34.2pp** |
| 体力 `stamina` | 耐久：池子越空落点越飘越晚，后半段开始漏 | 2.0pp / **10.8pp** |
| 体力回复 | 一只手空档超过 400ms 的部分按 60/秒回体力，回满为止 | 密谱几乎回不到（RC2 终盘 +7pp），稀疏谱因为本来就满池，回复大多被"不能超过满池"削掉 |
| 准度 `avg_accuracy` | 落点误差的地板（**曲线**，见下；只影响打得多准，不会凭空漏键） | 简单谱上大 P 率能差 20~40pp / 高难谱 6~10pp（旧版线性时简单谱几乎为 0） |
| 稳定 `consistency` | 长条**松手**的精度 + 每局手感幅度（不影响按下的精度） | 0.9pp / 1.4pp；另有手感幅度：稳定 14 手感 ±18，稳定 100 手感 ±5 |
| 心态 `mentality` | 连击 **>500** 且**体力已经吃紧**（疲劳 > 0.25）时"手抖一下"：落点被推后约 120ms，判成 BAD 或擦边 MISS | 0.15pp / 0.38pp；体力宽裕的谱（低难图）**完全不会触发**，只在长连击 + 体力吃紧的后半段出现 |

### 判定窗口跟着谱面 OD 走

`[judge] follow_chart_od = true`（默认）时，每张谱按自己的 `OverallDifficulty` 重算窗口，
用的是 lazer 的 mania 窗口曲线 —— 源码 `ManiaHitWindows.cs` 给的是 **OD0 / OD5 / OD10** 三个点：

| 本项目 | lazer | OD0 | OD5 | OD10 |
| --- | --- | --- | --- | --- |
| `perfect_g` | Perfect | 22.4 | 19.4 | 13.9 |
| `perfect` | Great | 64 | 49 | 34 |
| `great` | Good | 97 | 82 | 67 |
| `good` | Ok | 127 | 112 | 97 |
| **`bad`** | **Meh** | 151 | 136 | 121 |
| —（算 miss） | Miss | 188 | 173 | 158 |

区间之间按 `DifficultyRange` 折线插值（`mid + (max-mid)×(OD-5)/5`，OD<5 时同理向下），
最后 `floor(x) + 0.5`，所以结果都是 x.5。OD 超出 0~10 会外推（与 lazer 一致，不截断）。

例：TB 谱 OD 7.8 → 窗口 16.5 / 40.5 / 73.5 / 103.5 / 127.5 ms；
OD10 才是 13.5 / 34.5 / 67.5 / 97.5 / 121.5。

- **`bad` 对标的是 lazer 的 Meh**（不是 Miss）—— 本项目没有单独的 Miss 窗口，
  超出 `bad` 就直接算漏键；lazer 那个 Miss 窗口（OD10 时 158.5ms）是"音符过期"的时间；
- 关掉开关（`follow_chart_od = false`）时，固定用配置里那五个值；
- 每局开局会在控制台打印本谱的 OD 与实际生效的窗口，方便核对。

### 计分：照搬 osu!lazer 的 mania 方案

分数**整段照搬 osu!lazer**（源码 `osu.Game.Rulesets.Mania/Scoring/ManiaScoreProcessor.cs`），
所以模拟出来的分数和真实 lazer mania 是同一套口径：

```
总分 = 150000 × 连击进度
     + 850000 × 准度^(2 + 2×准度) × 准度进度
     + bonusPortion（mania 没有 bonus 判定，恒为 0）

连击分增量 = 基础分 × clamp(log4(当前连击), 0.5, log4(400))
准度      = Σ基础分 / (已判定次数 × 305)
判定权重   = Perfect 305 / Great 300 / Good 200 / Ok 100 / Meh 50 / Miss 0
```

几个要点：

- **连击只占 15%，准度占 85%**，而且准度要开 `2+2×准度` 次方（高准度时约等于 4 次方）——
  这是 lazer mania 最反直觉的地方：1% 的准度差距大约值 4% 的那个 85 万分项；
- **连击乘数是 log₄**，从 0.5 爬到 4.322，**连击 400 就封顶**，之后不再涨；
- 三个"进度"都是"拿到多少 / 总共能拿多少"，所以**分数是随谱面推进爬到 100 万**的；
  「总共能拿多少」按 lazer 的做法来：`ApplyBeatmap()` 里会 **`SimulateAutoplay()` 把整张谱
  全 Perfect 自动播放一遍**，用那一遍的值当满额。所以连击乘数从 0.5 往上爬的过程两边一致 ——
  **全大 P 正好是 1,000,000**（任何谱长都精确等于 100 万，测试里有断言）；
- 五档判定和 lazer 一一对应：本项目的 `perfect_g/perfect/great/good/bad`
  ↔ lazer 的 `Perfect/Great/Good/Ok/Meh`；
- 权重写在 `src/entities/player.py` 的 `ACCURACY_BASE` / `COMBO_BASE_SCORE`，
  **不再由 config.toml 控制**（老配置里的 `[judge] score/bonus` 会提示已失效）。

`data/_selftest/lazer_score_test.py` 会把同一串判定同时喂给本实现和一份照着 lazer 源码
写的参考实现，**12 个场景逐个比对到 0.000000 分**，用来防止以后改动跑偏。

#### 屏幕上的实时分数：只换尺子，不动计分

上面那套原始分是 **S 形**的：`150000×连击进度 + 850000×准度⁴×准度进度` 里那一项
"准度进度"是 `已判定/总判定`，它自己线性，但前面乘的 `准度^(2+2×准度)` 用的是
**累计基础分占比**（已经打过的部分里大 P 占多少）—— 这个量在开局接近 0、中盘只有 0.5，
被四次方一放大就只剩 0.0625，于是前段分数被压得极扁。实测 Science [Easy] 全 Perfect：
进度 25% 才 3.4 万、50% 才 12 万，最后 10% 猛涨 35 万。

但比赛录像里看到的是**线性**的（MWC 2026 的实时计分：70% 进度 ≈ 70% 分数）。
所以屏幕口径 `Player.display_score` 把指数里那个量换成**当前平均准确率**
（`self.accuracy/100`，开局就是 1.0，只在真打丢时才掉）：

| 进度 | 10% | 25% | 50% | 70% | 90% | 100% |
| --- | --- | --- | --- | --- | --- | --- |
| 原始分（计分用） | 1.0 万 | 3.6 万 | 12.1 万 | 27.8 万 | 64.7 万 | 100 万 |
| 显示分（屏幕上） | 9.5 万 | 24.2 万 | **49.3 万** | **69.6 万** | 89.9 万 | 100 万 |

- **计分一个字没动**：`score` / `std_score` 仍然是那套原始分，赛果、Excel、结算榜、
  控制台全用它，`lazer_score_test.py` 依然逐位一致；只有游玩界面那个数字和队伍总分
  走 `display_score`；
- **曲终两者等价**（都等于本局最终准确率），所以最后一帧显示的就是真实最终分，不会跳；
- 失误照常反映：准确率掉一点，显示分就落到满分线下面；
- 单调性：干净局完全不回跳；难谱断连时可能有 ≤300 分/次的微小回落（不到 0.03%），
  对排名没有影响。

`data/_selftest/realtime_score_test.py` 守着这条口径（线性 / 曲终一致 / 不回跳 /
全 Perfect 仍是 100 万）。

### 落点误差模型
每个音符**只结算一次**（在它到点的那一帧），选手一定会去按 —— 没有"按不按键"的随机，
只有"按下去的时刻偏了多少"：

```
press_offset = μ + N(0, σ) + 慢漂移 + 手抖
σ = 准度地板×β(1.5~26ms，见下) + 密度压力²×38 + 疲劳×15
μ =                          密度压力²×50   + 疲劳×22
密度压力 = max(0, 手速决定的间隔 / 实际同键间隔 - 1)
慢漂移   = 每只手一条，逐判定演化：drift ← drift×0.94 + N(0, 2.5ms)
手抖     = 连击>500 且体力吃紧时，按概率给落点加 N(120ms, 45ms)
判定 = get_judgement(press_offset)   超过 bad 窗口 = 漏键
```

#### 「慢漂移」：让高准选手不再必然全大 P

只有白噪声的模型下，**σ ≤ 3ms 就意味着"725 个音符全落在大 P 窗口（±17ms）里"是必然事件**
（单音符掉出去 ~1e-5，全对 ~99%）。于是高准选手打简单谱永远是 100% 大 P、准确率 100.000% ——
一眼假。真人不是"每一下都贴着中心"，而是**整段偏一点**（打早/打晚一个稳定的量，几十秒内来回摆）。

所以每只手加了一条漂移（`TIMING_DRIFT_SIGMA` / `TIMING_DRIFT_DECAY`），
逐判定演化 `drift ← drift×衰减 + N(0, σ)`，稳态幅度 ≈ `σ/sqrt(1−衰减²)` ≈ **7.3ms**：

| Science[Easy]（732 判定） | 大 P 率 | 准确率 | 一局 GREAT | 得分 |
| --- | --- | --- | --- | --- |
| 加漂移前·准度 100 | **100.00%** | 100.000% | 0 | 1,000,000 |
| 加漂移后·准度 100 | 97.6% | 99.961% | 0~3 | 998,682 |
| 加漂移前·准度 90 | **100.00%** | 100.000% | 0 | 1,000,000 |
| 加漂移后·准度 90 | 95.3% | 99.923% | 0~4 | 997,391 |
| 加漂移后·准度 40 | 74.1% | 99.367% | 4.7 | 978,440 |

- 漂移是**按时间**演化的（每判定一步），所以偏差**成段出现**，曲线上一眼看得出"人的痕迹"；
- 它和准度、体力、手速**完全独立**，所有选手一视同仁（不是又一条能力值）；
- **副作用（预期内）**：真实对局里"打完一局全大 P"不再是必然，所以端到端断言从
  "精确 100 万"改成了"≥ 99 万 + 大 P 率不再贴 100%"；
  而喂固定判定串的 `lazer_score_test.py` 不受影响（计分公式一个字没动，仍逐位一致）。

#### 准度地板是一条曲线，不是直线

「准度」是 σ 里**唯一**由准度决定的那一份（另外两项是手速和体力的活）。
它以前写的是线性：`σ = 1.5 + 10.5 × (1 − 准度/100)`，结果是**简单谱上准度几乎没用** ——
简单谱判定窗口本来就宽（OD 6.5 的大 P 是 ±21ms），线性映射下准度 40 的 σ 才 7.8ms、
准度 80 只剩 3.6ms，两者都远在窗口里面，打出来的大 P 率 97% 对 100%，
准确率只差 **0.04pp**：换个人名在简单谱上几乎看不出区别。

现在这一项走 `TIMING_SIGMA_ANCHORS` 这张锚点表（分段线性插值，超出两端取端点），
再叠一层「中段鼓包」（见下面「整体难度调整」）：

| 准度 | 0 | 20 | 30 | 40 | 60 | 70 | 80 | 90 | 95 | 100 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 锚点表 σ（ms） | 26.0 | 17.2 | 14.2 | 10.3 | 5.4 | 6.2 | 5.6 | 3.2 | 2.4 | 1.5 |
| **实际 σ**（鼓包 ×1.25） | 26.0 | 17.2 | **14.2** | **12.9** | **6.8** | **7.8** | **7.0** | **4.0** | **2.4** | 1.5 |

60 及以下与原来那条光滑曲线完全一致；**70~80 被特意顶高**（削弱中高准），**85 以后迅速压到地板**
（凸显超高准）。为什么不能继续用光滑曲线：OD6.5 的大 P 窗口有 ±17ms，正态分布下 **σ 低于 ~4ms
大 P 率就是 100.0000%**，而光滑曲线在准度 70 时 σ 已经掉到 3.7ms —— 70/80/85/90/100 全被拍平在
"全大 P"上，高准段毫无含金量，差距全挤在 20~60。实测（Science[Easy]）：

| 准度 | 20 | 40 | 60 | 70 | 80 | 90 | 100 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 更早（光滑曲线）大 P 率 | 67.0% | 90.2% | 99.7% | **100.0%** | **100.0%** | **100.0%** | 100% |
| 锚点表大 P 率 | 64.6% | 90.4% | 99.7% | **99.5%** | **99.7%** | **100%** | 100% |

**物理天花板还在**：大 P 与普通 P 只差 5 点权重（305 vs 300），所以哪怕大 P 率从 100% 掉到 84%，
总分也只差 0.5% —— 想让高准段拉开更大，只能再动权重（`ACCURACY_BASE`），那是另一件事。

另外，低准度选手在简单谱上依然**不漏键**（设计上准度就没有"随机漏键"通道），
只是明显地从大 P 掉到普通 P —— 准度 20 与 90 的准确率能差 1.1pp、一局差 3.8 万分。

#### 整体难度调整：只压准度中段

要让"除两端之外整体变难"，加了一层**只作用于准度中段的鼓包**（`TIMING_SIGMA_MID_BOOST`）：

```
σ_准度 = 锚点表(准度) × 鼓包系数
鼓包系数 = 1.0                     准度 ≤ 30（低准度本来就差，不再压）
         = 1.25（TIMING_SIGMA_MID_BOOST）   准度 40~90（这一段整体变难）
         = 1.25 → 1.0 线性收回       准度 90~95（避免"准度 90 比 95 差一截"的断崖）
         = 1.0                     准度 ≥ 95（超高准的含金量不受影响）
```

四条边界（`TIMING_SIGMA_MID_BOOST` / `..._FLOOR` / `..._EDGE`）都是常量，按需微调。
实测效果（大 P 率下降即分数下降；30 与 95 两档严格不动）：

| 谱面 | 准度30 | 准度50 | 准度70 | 准度85 | 准度90 | 准度95 |
| --- | --- | --- | --- | --- | --- | --- |
| Science[Easy] | 98.37 → **98.37** | 99.86 → **99.56** | 99.97 → **99.87** | 100.00 → **99.98** | 100.00 → 100.00 | 100.00 → **100.00** |
| Science[Love!] | 97.58 → **97.58** | 99.65 → **99.26** | 99.82 → **99.66** | 99.92 → **99.86** | 99.97 → **99.93** | 99.97 → **99.97** |
| Vacant[Varium] | 95.65 → **95.65** | 96.55 → **96.37** | 96.63 → **96.56** | 96.68 → **96.65** | 96.72 → **96.69** | 96.72 → **96.72** |

注意难谱上幅度天然很小 —— 上一节的"压力衰减"已经把准度地板压到接近 0，所以那张谱本来就
不靠准度分高下（这是设计好的）。要更大的降幅只能动权重或体力/手速机制。

#### 准度只该在"其它压力很小"的时候说了算

上面那条曲线只解决了"简单谱上准度分不出高下"，还有第二个问题：**准度地板是绝对毫秒数**
（1.5~26ms），它不知道谱面有多难。难谱上体力/密度已经顶着一份大误差（实测 Vacant 的
疲劳项均值就有 5.1ms、峰值疲劳 0.705），准度地板再以满额叠上去，σ 就会跨过 bad 窗口 ——
变成"准度低的人**漏键**"，也就是准度跑到难谱上去决定生死了。而设计要求是：

> **准度主要影响简单曲目里小 P（普通 P）的出现频率，不该在考验上限的谱上搅局。**

所以准度地板按"选手当前承受的其它压力"打折（`TIMING_SIGMA_DAMP_K`）：

```
σ = 准度地板 × β + 密度项 + 疲劳项
β = exp( -( (密度项 + 疲劳项) / TIMING_SIGMA_DAMP_K )² )     # 默认 K = 3
```

- **只压准度地板**，手速（密度项）和体力（疲劳项）一份都不动 —— 难谱的生死仍然归它们；
- 用平方指数而不是 `1/(1+s/k)`，是为了"中间档还吃准度、难档迅速失效"；
- 逐音符生效：一首歌里稀疏段照常吃准度，爆发段不吃。

| 其它两项之和 | β |
| --- | --- |
| 0ms（简单谱） | **1.00**（准度满额） |
| 1.6ms（Science[Love!]） | 0.75 |
| 5.1ms（Vacant） | **0.05**（准度基本退场） |

实测（手速/体力固定，只动准度，同批种子）：

| 谱面 | 档 | 准度 20→100 的分数差 | 准度 20 的漏键 | 通道 |
| --- | --- | --- | --- | --- |
| Science[Easy] OD6.5 | 简单 | +3.8 万（满分 3.8%） | 0 → 0 | 大 P 率 64%→100% |
| PixelPlanet[Norm] OD7.4 | 中等 | +4.7 万 | 0 → 0 | 大 P 率 62%→100% |
| Science[Love!] OD8.5 | 较难 | +5.0 万（改前 +10.2 万） | 0 → 0 | 大 P 率 68%→100% |
| Vacant[Varium] OD7.8 | 密谱 | +2.4 万（改前 **+24.4 万**） | **0**（改前 17.3） | 大 P 率 70%→82% |

（Vacant 的绝对分差比简单谱大，是因为它有 7700 次判定、简单谱只有 732 次；按占满分算，
密谱 2.4% 对简单谱 0.53%，密谱不再是"准度说了算"的地方。）

同时确认难谱的分化还在**手速/体力**手里（`speed_sensitivity.py`：手速极差 24.8pp、漏键 247→0），
准度的影响力被压到 1.4pp（改前 11.5pp）。

调参入口都在 `src/entities/player.py`：`TIMING_SIGMA_ANCHORS`（上面那张锚点表）、
`TIMING_SIGMA_DAMP_K`（压力衰减陡度，填很大就退回"准度不衰减"）、
`TIMING_SIGMA_MAX` / `TIMING_SIGMA_MIN`（两端值）。
`ability.py` 打印的 σ 和游戏用的是同一个函数（`timing_sigma_for()`），改一处两边都变；
标定用 `data/_selftest/accuracy_curve_sweep.py`（新旧曲线逐档对照）与
`data/_selftest/accuracy_channel_probe.py`（逐档拆解"准度是通过哪条通道影响分数的"）。

**长条松手**是另一次判定，口径与点击有三处不同：

```
release_offset = μ + N(0, σ)
σ = (准度地板×β + 疲劳×15 + 不稳定×3) × 1.8   # 唯一吃「稳定性」的地方；β 同上
μ =             疲劳×22                         # 不吃手速、也不消耗体力
```

也就是说**稳定性只作用在松手上**：按下那一下不看稳定（实测稳定 0 与 100 的按下 σ 完全一致），
松手却随稳定明显变化（稳定 0 的松手 σ 比稳定 100 大 3.6~5.7ms）。
稳定性另一个作用仍然是**每局手感幅度**（稳定 14 → ±18，稳定 100 → ±5，`form_range=20` 时）。

漏键只有两个来源，都是"有原因"的：
1. **跟不上 / 累了** —— 密度压力和疲劳把 σ、μ 顶上去，误差真的超出判定窗口；
2. **心态手抖** —— 连击 **>500**、**并且体力已经吃紧**（疲劳 > 0.25）时才会发生，
   表现为 BAD 或擦边 MISS。压力大小取"还剩多少体力"的补数并带死区，
   所以体力宽裕时**根本不会掷这个骰子**：低难图（几乎不掉体力）配上合格的耐力
   可以稳定 FC，压力天然集中在长歌后半段和密谱上。

   实测（每档 6 局，手速 80 / 准度 70 / 稳定 70）：RC1 这种低难图在
   心态 90~0、体力 90~30 的所有档位都是 **6/6 FC、0 次手抖**；
   而 RC2 那种硬谱仍随心态明显分化（90 心态 0.8 次/局 → 0 心态 4.2 次/局）。

   「自己分高」和「进入赛点」会再放大这个概率，但**计分赛不会吃赛点倍率**
   （那个模式下没有"再赢一局就夺冠"这回事）。

### 为什么无 UI 不会算错

推进步长从 16.7ms 放到 300ms，结果**逐位相同**（本机调试脚本里对这一点有断言）。
为了做到这点顺手修了两个模型本身的帧率依赖：

1. **结算顺序**：原来一帧里"先把所有点击判定做完，再做所有长条松手判定"，
   跨越同一帧的一次点击和一次松手谁先结算会取决于帧长。现在 `play()` 每次只挑
   **最早该结算的那一个**再重新挑，严格按时间顺序结算。
2. **随机流**：6 名选手原来共用全局 `random`，各人抽数的先后会随"这一帧谁结算了几个音符"变化。
   现在**每个选手一条独立的 `random.Random`**（种子从全局流取，所以 `random.seed(N)` 仍可复现整场）。

### 体力是怎么算的

两只手各有一个 10000 的池子（左手轨道 0/1、右手轨道 2/3），`fatigue` 取两手的平均值。
**每首歌开始时满血重置**（跨曲不累积），一首歌之内：

- **消耗**：每按一下扣 `3 × clamp(250/同键间隔, 0.4, 3) ÷ 效率`，效率 = `0.4 + 1.2 × 体力/100`。
  越密越费，而且有个 0.4 的地板 —— 所以"音符本身存在"就占了总消耗的 30~40%；
- **回复**：这只手距离上一次出力**空档超过 400ms** 的部分，按 **120/秒** 回体力，回满为止。
  注意回复看的是"整只手"的空档，不是单条轨的间隔 —— 两条轨轮流砸的时候轨间隔可能不小，
  但那只手其实一直在动。

所以体力是**大进大出**的：密段哗哗掉，空档又哗哗回。实测（体力 50、终盘 / 最低 / 摆幅）：

| 曲目 | 终盘 | 最低 | 摆幅 |
| --- | --- | --- | --- |
| RC1（稀疏） | 78% | 78% | 22 |
| RC2（最密） | 22% | 18% | 82 |
| RC3 / LN1 / HB1 | 67% / 67% / 69% | 同左 | 32~33 |

要保住"终盘 40%"所需的体力：RC1 只要 1，RC3/LN1/HB1 要 14~20，RC2 要 70。

**只有 miss 会断连**（BAD 不断连），所以手抖的那一下多半表现为掉分 + 偶尔断连。

**准度没有"随机漏键"通道**：它只决定 σ 的地板，所以低准度选手是"判定差、分数低"，
而不是"时不时莫名漏一个"。

### 长条（LN）

谱面里的长条是 `type` 带 128 位、末位带结束时间的行：

```
448,192,25078,128,0,26641:0:0:0:0:
  x    y   开始  类型 音效  └ 结束时间
```

- **渲染**：一个和普通音符完全一样的头（白色 35×10），加一条**颜色更深、更窄**的身
  （深灰 `(110,110,110)`、21px 宽），从头上方一直连到结束时间的位置；
  已经按住时头不再绘制，身则从判定线往上保留。受"挡板"限制，
  身体和普通音符一样只在最后约 400ms 的窗口里可见（`max_render_dist` 决定）。
- **判定**：头打中才开始按住，**松手时还有一次额外判定**。松手判定和点击判定的区别只有两条：
  1. **不吃手速** —— 它不算同键间隔，因此没有密度压力项，也**不消耗体力**
     （手速只作用于点击判定）；
  2. 更容易打偏 —— 落点误差 σ 乘 `LONG_RELEASE_SIGMA_SCALE`（默认 1.8）。

  其余（准度地板、疲劳、稳定性、判定等级、分数、连击）和点击完全一样。
- 头没打中 → 整根算一次 miss，不再有松手判定；松手判定 miss 同样断连。
- 满分按**判定次数**算：普通音符 1 次、长条 2 次（`Song.judgement_count`），
  所以插了长条不会让标准化分数虚高。

### 画面上的判定计数

游玩中每个选手的演奏区两侧各有一列竖排小字，每行一个判定、顺序固定：

| 行 | 判定 | 颜色 |
| --- | --- | --- |
| 1 | 完美+ `perfect_g` | 黄 |
| 2 | 完美 `perfect` | 橙 |
| 3 | 很好 `great` | 绿 |
| 4 | 好 `good` | 蓝 |
| 5 | 差 `bad` | 淡灰 |
| 6 | 漏 `miss` | 红 |

数量为 0 的那一行不画字，但**行位保留**，所以红色的 miss 永远落在第六行。

- 第一队（红队）贴在**第四轨右侧**，左对齐；
- 第二队（蓝队）贴在**第一轨左侧**，右对齐。

字号由 `JUDGEMENT_COUNT_FONT_SIZE`、颜色由 `JUDGEMENT_COUNT_COLORS`（都在 `src/core/game.py` 顶部）控制。

漏键不是掷骰子掷出来的，而是"误差超出判定窗口"的结果。**σ 各项是相加的**，再加上准度地板的
**压力衰减**（见上面「准度只该在其它压力很小的时候说了算」），难度分化就分得很干净：

- **低难图**：密度压力≈0、几乎不疲劳 → β≈1，σ 基本只剩准度那一项 → 准确率都在 99% 上下，
  但大 P 率能从 64% 差到 100%，准确率差 1.1pp、一局差 3.8 万分 —— 胜负就在这里分；
- **高难图**：密度/疲劳已经把 σ 顶起来 → β 趋近 0，准度退场，**手速和耐力决定上限**
  （实测难谱上准度的分数影响只有 1.4pp，而手速极差 24.8pp、平均漏键 247→0）。

选手风格由名字哈希决定（手速型 / 耐力型 / 稳准型 / 爆发型 / 大心脏 / 赌徒 / 天才…），
风格给五项加不同偏置，所以"换个名字"就是换一个完全不同的人。

上面的数字来自本机的标定脚本（跑真实谱面做扫参），那些脚本属于调试工具，不进版本库；
版库里留的是 `data/_selftest/` 下那几份**带断言的回归**（见「自测与标定」一节）。

### 单独查一个名字：`ability.py`

想给选手起名字之前先看看他会拿到什么能力值，用这个独立小工具（不依赖 pygame、
不读谱面、不启动游戏，只跑名字哈希那一段逻辑，结果和游戏里完全一致）：

```bash
python ability.py Red-1                  # 查一个名字（基准 + 风格 + 手感 + 一局样例）
python ability.py Red-1 Red-2 阿夸        # 多个名字给表格（中英文自动对齐）
python ability.py --rolls 5 Red-1        # 连抽 5 局，看看手感波动范围

python ability.py --styles               # 打印 8 种选手风格各加什么偏置
python ability.py                        # 交互模式：一行一个名字，空行结束
```

手感幅度的默认值直接读 `config.toml` 的 `[players] form_range`，所以和游戏是同一套参数。

### 算赛谱的长条占比与能力要求：`chart_report.py`

把 `config.toml` 里所有赛谱扫一遍，算出**长条占比**和**手速/体力要求**，写成一份 Excel
（同样不依赖 pygame，只走谱面文本解析）：

```bash
python chart_report.py                          # 读 config.toml → data/chart_report.xlsx
python chart_report.py -c my.toml -o out.xlsx   # 指定配置与输出
python chart_report.py --free 0.03 --keep 30    # 调两个阈值
python chart_report.py --no-excel               # 只在控制台看
```

两个"要求"不是拍脑袋定的，而是**反推主程序那套落点误差模型**：常量直接从
`src/entities/player.py` import，主程序改模型时这份报告自动跟着变。

- **手速要求**：让整张谱的**平均密度压力**降到阈值（默认 0.05）以下所需的最低手速。
  密度压力 = `max(0, 所需间隔/同键间隔 − 1)²`，所需间隔 = `230 − 145 × 手速/100`。
  另外两列是同一口径的尖峰版本：
  **最快5%段手速**（段长 = 总音符数 × 5%，沿时间顺序滑动取最吃力的连续一段）
  和**最密处手速**（单点尖峰）。三者天然满足「全曲 ≤ 最快段 ≤ 最密处」。
- **体力要求**：打完这张谱后体力池平均还剩 `keep%`（默认 40%）所需的最低体力。
  每按一下消耗 `2 × clamp(250/同键间隔, 0.4, 3) ÷ 效率`，效率 = `0.4 + 1.2 × 体力/100`，
  所以可以解析反解，不用跑模拟。
- **长条占比** = 长条数 / 总音符数，判定与游戏一致（`type & 128` 且结束时间晚于开始时间）。
  表格里还有音符数、平均长条时长、每秒音符（中位/峰值）、同键间隔 P10/中位/P90 等辅助列。

写出的 xlsx 有**两张表**：

- **sheet1「赛谱分析」**：上面这些完整指标，表尾附口径说明；
- **sheet2「难度总览」**：只留最关心的 12 列，没有任何说明行，方便直接排序对比 ——
  `曲目 / 标题 / 标题原文 / 作曲者 / 时长(s) / 音符数 / 长条数 / 长条占比(%) / 手速要求 /
  最快5%段手速 / 体力要求 / 体力50终盘剩余(%)`。
  「标题」是 `config.toml` 里写的显示名，「标题原文」是谱面 `[Metadata]` 里的
  `TitleUnicode`（原作者写的原文，没有时退回 `Title`）；「作曲者」取谱面的
  `Artist` 字段（不是谱师 `Creator`），谱面没写时才退回 `config.toml` 的 `artist`。

本机的验证脚本会把解析结果和真实模拟器对撞：实测
「体力 50 时的终盘剩余体力」解析值与模拟值完全吻合（82.1/82.1、45.9/45.9、26.8/26.8），
手速要求也正好卡在压力阈值上。

## 自测与标定

`data/_selftest/` 下是**带断言的无头回归**（都不需要真实窗口，会自己把 SDL 设成 dummy）。
改判定/计分/能力模型之后挨个跑一遍，比肉眼盯对局可靠：

| 脚本 | 断言什么 |
| --- | --- |
| `pick_highlight_test.py` | 选曲页两阶段：第一阶段不高亮、点出后高亮落在选中行、第 2 轮先高亮上一轮 |
| `phase_flow_test.py` | 阶段流转：两阶段选曲 / preroll 之后才滚谱 / 音乐衔接 / 倒计时连续 / prelude 四种写法 |
| `selftest.py <config.toml>` | 跑真实主循环：状态机、判定、结算、赛果写回 |
| `lazer_score_test.py` | 计分与 lazer 参考实现**逐位一致**（12 个场景，0.000000 分） |
| `od_windows_test.py` | 判定窗口随 OD 的插值与 lazer 源码一致 |
| `accuracy_spread_test.py` | **准度只在简单谱上决定小 P 频率**、难谱/密谱上不制造漏键、按下不吃稳定性 |
| `realtime_score_test.py` | **屏幕分数随进度线性**、曲终回到原始分、不回跳（计分本身没动） |
| `headless_test.py` | 无 UI 模式：不弹窗、步长无关、赛果表两种模式都写且一致 |
| `consistency_test.py` | 稳定性只作用于长条松手 + 每局手感幅度 |
| `long_note_test.py` | 长条解析、两次判定、不吃手速、不耗体力 |
| `chart_report_test.py` | 长条占比/手速要求/体力解析与模拟对撞 |
| `score_mode_test.py` | 计分赛：曲目顺序、名次、Excel、**成绩表 UI（只有总分+排名，无胜负字样）** |

标定用的**扫参工具**（只打印表格、不断言，用来给上面的参数定值）：

```bash
python data/_selftest/accuracy_sensitivity.py            # 当前参数在各谱面上的准度分化
python data/_selftest/accuracy_sensitivity.py --names    # 换成 config.toml 曲库里的谱面
python data/_selftest/accuracy_curve_sweep.py --detail   # σ 曲线：旧光滑 vs 新锚点逐档对照
python data/_selftest/accuracy_channel_probe.py          # 准度是通过哪条通道影响分数的（漏键/大P率）
python data/_selftest/difficulty_curve.py --stat stamina # 能力值 → 表现的整条曲线（调难度用）
python data/_selftest/difficulty_lever.py                # 体力消耗/回复、长条松手 σ 的几组参数对比
python data/_selftest/speed_sensitivity.py               # 手速/准度在难谱上的敏感度对照
```

准度那条 σ 曲线（`TIMING_SIGMA_ANCHORS`）就是拿 `accuracy_curve_sweep.py` 扫出来的：
先在 `Science [Easy]`（OD 6.5、4 NPS）上定"70~80 要掉、90+ 要留住"，
再拿 `Science [Love!]`、`Vacant Rhapsody`（OD 8.5 / 7.8、13~17 NPS）当对照。
压力衰减系数 `TIMING_SIGMA_DAMP_K` 则是拿 `accuracy_channel_probe.py` 定的 ——
那张表把"准度造成的分数差里有多少来自漏键、多少来自大 P 率"拆开看，
改动前后分别量一次就知道衰减有没有生效（Vacant 上漏键 17.3 → 0）。
整体难度的「中段鼓包」用 `difficulty_curve.py` 逐档核对（30 与 95 两档必须纹丝不动），
`difficulty_lever.py` 则用来预演体力/长条那两根杆的力量与副作用。
